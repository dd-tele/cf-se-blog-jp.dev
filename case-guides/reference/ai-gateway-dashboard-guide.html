00

はじめに

Cloudflare ダッシュボードの「AI ＞ AI Gateway」で取得したスクリーンショットをもとに、ゲートウェイの各タブに表示されるすべての項目について、意味と仕組み、確認すべき点を解説します。

本資料の読み方

  • 各節は「スクリーンショット → 画面の役割 → 項目の詳細 → 仕組み → この環境での読み取り」の順で構成しています。
  • スクリーンショットはクリックすると拡大表示できます。
  • 機能名は「ダッシュボードの表記（英語の正式名称）」の形で併記しています。ドキュメントを検索するときは英語名を使うと確実です。
  • 仕様は Cloudflare Docs（2026 年 10 月時点）に基づきます。ベータ表示の機能（プロバイダーキー、動的ルート、支出上限）は、今後仕様や表記が変わる可能性があります。
  • 「概要」タブのスクリーンショットは今回取得していないため、解説の対象外です。
共有時の注意図 4-4（Access）には利用者のメールアドレス、図 5-3（支出・セキュリティ）にはアカウント ID が写っています。社外に共有する場合は、該当箇所をマスクしてください。

AI Gateway の役割

AI Gateway は、アプリケーションやエージェントと AI プロバイダー（OpenAI、Anthropic、Workers AI など）の間に入るプロキシです。接続先の URL を AI Gateway のエンドポイントに変えるだけで、既存の SDK とコードをほぼそのまま使えます。経由したすべてのリクエストに対して、次の 4 つの機能を一か所で提供します。

→
保護ファイアウォール・Access・認証
危険な内容と機密データの送受信を検査
→
統制Policies・支出上限・レート制限
利用者や予算ごとに利用を制限

可用性キャッシュ・リトライ・動的ルート
障害時の再試行と別モデルへの切り替え
補足アプリケーションセキュリティの「AI Security for Apps」は、外部の利用者から自社の AI アプリへの入力を WAF で検査する機能です。AI Gateway は、自社のアプリやエージェントから AI プロバイダーへの通信を制御します。守る方向が異なるため、両方を組み合わせて使えます。

ユーザーインサイト（主要指標）

User Insights は、AI Gateway の支出と利用を利用者（ID）別に集計する画面です。追加料金や設定は不要ですが、利用者を識別するには次のいずれかが必要です。識別できないリクエストは「未確認」の 1 つの ID にまとめられます。

  • リクエストにカスタムメタデータ（cf-aig-metadata ヘッダー）でユーザー ID を付ける

タスクとモデルの分析

リクエストの内容をタスク（デバッグ、コードの設計、文章の作成など）に分類し、使ったモデルがタスクに見合っているかを Overkill（過剰）、Appropriate（適切）、Underpowered（不足）、Could not assess（判定不能）で評価します。設定タブのログ分類を有効にすると利用できます（5-1）。高価なモデルを簡単なタスクに使っている箇所を見つけ、コストを下げる手がかりになります。

03

ファイアウォール

プロバイダーに届く前にプロンプトを、利用者に返す前にレスポンスを検査します。有害な内容とプロンプトインジェクションを Guardrails が、機密データを DLP が検出します。

Guardrails

Guardrails は、Workers AI 上の安全性判定モデル（Llama Guard）でプロンプトとレスポンスを分類し、危険なカテゴリに該当した場合にフラグを付けるかブロックします。プロバイダーやモデルを問わず、同じ基準を適用できます。

要素意味
トグル（右上）Guardrails 全体の有効・無効です。本環境は有効です。
NOTEすべてのリクエストで追加の Workers AI 推論が実行され、標準の Workers AI 料金がかかります。ログの「Guardrails scan」がこの推論です。
プロンプトのモデレーション利用者の入力を、プロバイダーに送る前に検査します。ブロックした場合、プロバイダーへのリクエストは行われません。
レスポンスのモデレーションモデルの出力を、利用者に返す前に検査します。
アクションカテゴリごと・方向ごとに選びます。無視（検査しない）、フラグ（通過させてログに記録）、ブロック（拒否してエラーを返す）。

データ損失防止（DLP）

AI Gateway DLP は、Cloudflare One の DLP と同じ DLP プロファイルを使い、プロンプトとレスポンスに含まれる機密データを検出します。社内の Web 通信向けに定義したルールを、AI の通信にもそのまま適用できます。

要素意味
トグル（右上）DLP 全体の有効・無効です。
Policies ＞ Add Policy検出の単位となるポリシーを追加します。ポリシーは複数作成でき、それぞれ個別に有効・無効を切り替えられます（右上のトグルとごみ箱）。
Policy IDポリシーの名前です（鉛筆アイコンで変更）。ログの判定結果に表示されます。
DLP プロファイル検査に使うプロファイルです（複数選択）。「Manage profiles」から Cloudflare One の DLP 設定に移動します。
Actionいずれかのプロファイルに一致したときの動作です。Flag（記録のみ）または Block（拒否）。
Check検査の対象です。Request（プロンプト）、Response（レスポンス）、または両方。

この環境での読み取りPolicy 1 が、リクエストとレスポンスの両方をブロックで検査しています。プロンプトに認証情報や個人情報を貼り付けて外部モデルに送信する事故を、ゲートウェイの時点で止められる構成です。

04

接続と制御

プロバイダーとの接続（キー、ルート）と、ゲートウェイの入口（ドメイン、認証、ポリシー）を設定するタブです。

プロバイダーキー（BYOK）

BYOK（Bring Your Own Keys、保存されたキー）は、各プロバイダーの API キーを Cloudflare の Secrets Store に保管し、リクエストの実行時にゲートウェイが注入する仕組みです。アプリのコードや環境変数にプロバイダーのキーを置かずに済み、キーのローテーションもダッシュボードで完結します。

要素意味
利用可能（プロバイダー一覧）キーを登録できるプロバイダーです。Adobe Firefly、Amazon Bedrock、Anthropic、Azure、Google AI Studio、Google Vertex AI、OpenAI、Mistral、Groq、DeepSeek、Perplexity AI、OpenRouter など。「追加」からキーを登録します。
リクエスト例保存されたキーを使う場合、プロバイダーの Authorization ヘッダーは不要です。ゲートウェイの認証トークン（cf-aig-authorization）だけを送ると、"default" エイリアスのキーが自動的に使われます。
キーエイリアスの使用同じプロバイダーに複数のキーを登録した場合、cf-aig-byok-alias: production のようにヘッダーでキーを選びます。本番と検証、部署ごとにキーを分けると、プロバイダー側の請求も分けられます。
キーのテスト登録したキーで小さなリクエストを送り、有効か確認します。プロバイダー側で課金が発生する場合があります。
カスタムプロバイダー一覧にないプロバイダー（社内の推論基盤など）をアカウント設定で定義すると、ここでキーを登録できます。
この環境での読み取りスクリーンショットの範囲には、登録済みのキーは表示されていません。現在の利用は Workers AI のみで、Workers AI は Cloudflare のアカウントで認証されるため、プロバイダーのキーは不要です。

動的ルート

Dynamic Routing は、リクエストをどのモデルに送るかを、コードではなくゲートウェイ側のフローで決める機能です。アプリはモデル名の代わりに "model": "dynamic/my_route" とルート名を指定します。

要素意味
サンプルから開始（推奨）「gpt-4o（OpenAI）に送り、エラー時は Workers AI の Llama に自動で切り替える」テンプレートです。図のオレンジの点がフォールバックの分岐です。
ゼロから開始空のフローから独自のルールを組み立てます。
ルート名アプリから指定する名前です。作成後は変更できません。
使用例OpenAI 互換の SDK から呼び出すコードの例です。

フローで使える主な要素

要素用途の例
条件メタデータ（部署、プラン、ユーザー ID など）に応じてモデルを分けます。
割合トラフィックの一部だけを新しいモデルに送り、品質を比較します（A/B テスト、段階的な切り替え）。
レート制限・支出上限上限に達したら、安価なモデルに切り替えるか拒否します。
フォールバックプロバイダーの障害やエラー時に、別のプロバイダーのモデルで応答します。
説明時のポイントモデルの変更や切り替えのルールをアプリから切り離せるため、新しいモデルへの移行やプロバイダー障害への備えを、アプリを改修・デプロイせずに行えます。本環境ではまだルートは作成されていません。

Policies

Policies は、誰が・どのモデルやプロバイダーを・どこまで使えるかを定義するタブです。スクリーンショットはポリシーの作成画面です。

重要：最初のポリシーで既定の動作が変わりますポリシーが 1 件もないときは、すべてのリクエストが許可されます。1 件でもポリシーを追加すると、どのポリシーにも一致しないリクエストは拒否されます（既定の拒否）。本番環境では、全員を対象にした許可のポリシーを先に用意してから、個別の制限を追加します。
項目意味
Whoポリシーの対象者です。Everyone（全員）、User（特定の利用者）、Email domain ending in（メールドメイン）、Actor bucket（利用者のグループ）から選びます。利用者の識別には Access またはメタデータが必要です。
What（対象のモデル・プロバイダー）ポリシーを適用するモデルやプロバイダーです（スクリーンショットではドロップダウンに隠れています）。
アクションAllow until capped（上限まで許可）、Allow without a cap（上限なしで許可）、Block（拒否）。
Amount（USD）／Time window上限の金額と期間です。Monthly の場合、毎月 1 日 00:00 UTC にリセットされます（日本時間では 1 日の 9:00）。
Under what conditions?（任意）対象者の選択だけでは表せない条件を CEL で追加します。Builder（画面操作）と Raw CEL（式を直接記述）を切り替えられます。
Preview作成されるポリシーの要約です（例：Everyone spend cap ／ Limit to $100 / Monthly）。
補足Policies の詳細な仕様は、2026 年 10 月時点の Cloudflare Docs では確認できませんでした。本節は画面の表示から読み取った内容です。設定タブの「支出上限」（5-3）はゲートウェイ全体やメタデータ単位の予算、Policies は利用者単位の許可と上限、という使い分けと考えられます。

説明時に押さえる論点

  1. URL を変えるだけで始められる：既存の SDK とコードのまま接続先を切り替えるだけで、ログとコストの可視化がすぐに始まります。
  2. 利用者の識別が統制の前提になる：Access またはメタデータで利用者を識別すると、ユーザーインサイト、Policies、利用者単位の予算が使えるようになります。
  3. プロバイダーを問わず同じ基準で守れる：Guardrails と DLP は、OpenAI、Anthropic、Workers AI など、どのプロバイダーにも同じルールで適用されます。DLP は Cloudflare One のプロファイルを共有します。
  4. フラグで傾向を確認してからブロックする：Guardrails と DLP はどちらもフラグ（記録のみ）を選べるため、誤検知を確認してから段階的に強化できます。
  5. モデルの切り替えをアプリから切り離せる：動的ルートとリトライにより、プロバイダー障害やモデルの移行に、アプリを改修せずに対応できます。
