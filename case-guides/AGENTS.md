# 事例 - 設計ガイド 作成ルール（OpenCode 向け）

このフォルダ（`case-guides/`）で起動した OpenCode は、本書に従って「事例 - 設計ガイド」を作成する。
本書のパスとコマンドは、すべて `case-guides/` を作業ディレクトリとした相対パスで書いている。
毎回同じ構成・同じ体裁・同じ品質のアウトプットにすることを最優先とし、本書にない独自の構成や装飾を加えない。

---

## 1. 位置づけ

- サイト（Cloudflare Field Notes）では、コンテンツを次の 2 種類に分けている。
  - **記事**（`/posts`）: Markdown のブログ記事。本書の対象外。
  - **事例 - 設計ガイド**（`/cases`）: 導入事例の構成を、ダッシュボードの画面ごとに詳しく解説する HTML ガイド。本書の対象。
- 設計ガイドは「アーキテクチャの解説」と「ダッシュボードの詳細解説（リファレンス）」を兼ねる。
  読者は、左の目次から必要な画面だけを参照しても理解できること。
- 成果物は **SE が精査し、SE 自身の解説として公開する**。文章は SE が読者に直接説明する目線で書く。
- ページ構成の基準は `reference/ai-gateway-dashboard-guide.html`（AI Gateway ダッシュボード詳細解説）である。
  画像は含めていないため表示は崩れるが、章立て・節の書き方・文体の見本として参照する。
  `template/index.html` はこの CSS・スクリプト・章立てをそのまま引き継いでいる。

## 2. フォルダ構成

```
case-guides/
├── AGENTS.md              … 本書
├── template/
│   ├── index.html         … ガイドのテンプレート（CSS/JS は変更しない）
│   └── notes.md           … SE 入力メモのテンプレート
├── reference/             … 基準ガイド（AI Gateway）の HTML
├── scripts/package.py     … 検証と ZIP 作成
└── work/<slug>/           … ガイドごとの作業フォルダ（Git 管理外）
    ├── notes.md           … SE 入力メモ（ZIP に含めない）
    ├── raw/               … SE が撮影した元のスクリーンショット（ZIP に含めない）
    ├── assets/            … ガイドで使う画像（NN-kebab-case.png）
    └── index.html         … ガイド本体
```

- `<slug>` は英小文字・数字・ハイフンのみ（例: `zt-customer-a-2026-10`）。顧客名を含めない。
- `work/` と `*.zip` は `.gitignore` 済み。スクリーンショットや入力メモをコミットしない。

## 3. 作業手順

依頼を受けたら、次の順に進める。各ステップの完了時に、何をしたかを 1〜2 行で報告する。

1. **準備**: `work/<slug>/` がなければ作成し、`template/index.html` と `template/notes.md` をコピーする。
2. **入力の確認**: `notes.md` と `raw/` のスクリーンショットを読む。
   不足している必須情報（製品名、顧客エイリアス、画面取得日）があれば、作業を止めて SE に質問する。
3. **画面の棚卸し**: `raw/` の画像をすべて開いて内容を確認し、次の表を SE に提示する。
   `元ファイル名 → assets/ のファイル名 → 章・節 → 写っている機微情報（あれば）`
4. **マスキング確認**: メールアドレス、アカウント ID、IP アドレス、顧客ドメイン、テナント名、
   実在の人名などが写っている画像は、SE にマスク済みの画像を差し替えてもらう。
   **マスクされていない画像を assets/ に置いたり、ZIP に含めたりしてはならない。**
   画像を加工するツールで自動的にぼかすことはしない（見落としの原因になるため）。
5. **画像の配置**: 確認済みの画像を `assets/` にコピーし、`NN-kebab-case.png` にリネームする
   （例: `05-gateway-dns-policies.png`。`NN` は本文に登場する順の 2 桁連番）。`raw/` の元画像は消さない。
6. **章立ての決定**: 「4. ページ構成」に従い、画面の棚卸し結果から章と節の一覧（目次案）を作り、SE に提示する。
7. **執筆**: `index.html` のプレースホルダー `{{...}}` をすべて置き換える。仕様の説明は「7. 仕様の確認」に従って確認する。
8. **セルフチェック**: 「9. セルフチェック」をすべて確認する。
9. **パッケージ**: `python3 scripts/package.py work/<slug>` を実行する（`work/<slug>.zip` が作成される）。
   ERROR が 0 件になるまで修正する。WARN は内容を確認し、意図どおりでなければ修正する。
10. **報告**: 作成した ZIP のパス、章・節・図の数、SE に確認してほしい点（推測を含む記述、未取得の画面）を報告する。

## 4. ページ構成（固定）

### 4-1. 章立て

章番号は `00` からの連番で、次の順序を崩さない。機能章の数だけが製品と環境によって変わる。

| 章 | 名称 | 内容 |
|---|---|---|
| 00 | はじめに | 本資料の読み方 / 導入の背景と要件 / 〈製品〉の役割 / メニュー構成の全体像 / 〈通信・リクエスト〉の流れ / 接続方法 |
| 01 | 左ナビゲーションと共通要素 | 〈製品〉配下のメニュー / 画面上部の共通要素 |
| 02〜 | 機能章（複数） | ダッシュボードの左ナビの順に、画面のまとまりごとに 1 章 |
| 次 | 早見表 | 設定値・ヘッダー・ポリシー種別などの一覧 / 制御機能の使い分け / UI 表記の注意点 |
| 次 | この環境の所見 | 設定状況のまとめ / PoC・オンボーディングでの課題と対応 / 説明時に押さえる論点 |
| 最後 | 参考ドキュメント | 本文で参照した Cloudflare Docs の一覧 |

- 「導入の背景と要件」には `notes.md` の背景・契約概要・導入前の課題を載せる。入力がない行は表から削除する。
- 「PoC・オンボーディングでの課題と対応」は `notes.md` に入力がない場合は節ごと削除する（目次からも削除）。
- 取得していない画面の節は作らない。「本資料の読み方」に「解説の対象外」として列挙する。

### 4-2. 節の内部構成

機能章の各節は、必ず次の順で書く。該当する内容がない要素は省略してよいが、順序は入れ替えない。

1. **スクリーンショット**: `<figure><img src="./assets/NN-xxx.png" alt="..."><figcaption>図 章-連番　説明</figcaption></figure>`
2. **画面の役割**: 1〜3 文。初出の機能は `<b>英語の正式名称</b>` を含める。
3. **項目の詳細**: 罫線表。列は「要素 / 意味」または「項目 / 意味 / 本環境」。画面に表示されている項目は省略しない。
4. **仕組み**: 必要に応じて段落、`.flow`、`.note`（補足）で説明する。
5. **この環境での読み取り**: `<div class="tip"><b>この環境での読み取り</b>…</div>`。設定値から読み取れる設計意図と注意点。

### 4-3. タイトル

- `<title>` は `【導入アーキテクチャ】〈製品名〉：〈顧客エイリアス〉` とする（例: `【導入アーキテクチャ】Cloudflare Zero Trust：顧客組織A`）。
  アップロード時にサイトのタイトルとしてそのまま使われる。
- 目次上部の `.brand` は `〈製品名〉<br>設計ガイド：〈顧客エイリアス〉` とし、2 行目に対象（匿名化した呼称）と画面取得日を書く。

## 5. HTML の規約

- `template/index.html` の `<style>` と末尾の `<script>` は**一切変更しない**。インラインの `style` 属性も使わない。
- 使ってよい部品はテンプレートにあるものだけとする。
  - 構造: `section.chapter`（`id="chN"` と `data-title`）、`p.kicker`、`h1`、`p.lead`、`h3`（`id="sN-M"` と `data-title`）、`h4`
  - 本文: `p`、`ul`、`ol.list`、`table`（長文セルは `td.wrap`）、`code`、`b`
  - 図: `figure` / `img` / `figcaption`
  - 囲み: `.note`（補足）、`.tip`（読み取り・説明時のポイント）、`.warn`（共有時の注意・重要な挙動）
  - 図解: `.flow`（`.st` と `.ar` の段階図）、`.kpis`（大きな数値と小さなラベル）、`.grid2`
  - バッジ: `b-on`（有効）、`b-off`（無効・ベータ）、`b-log`（ログ・フラグ）、`b-block`（ブロック）、`b-risk`、`b-lbl`、`b-run`
- 目次（`#toc`）と本文は、章・節の id、番号、見出しを完全に一致させる。節を追加・削除したら目次も直す。
- 図番号は「図 章番号-章内の連番」（例: 図 3-2）。同じ画像を別の節で再掲する場合も新しい図番号を振る。
- 本文中の相互参照は `<a href="#s4-3">4-3</a>` の形式で、存在する節だけを指す。
- 画像は必ず `./assets/` からの相対パスで参照する。base64 埋め込み、外部 URL の画像、CDN の CSS・JS・Web フォントは使わない。
- `index.html` は 1.5MB 以下、ZIP は 30MB 以下。大きいスクリーンショットは PNG のまま解像度を保ち、不要な余白を切り取る。
- Mermaid などの外部スクリプトに依存する図は使わない。構成や流れは `.flow` と表で表す。
- サイトはガイドをサンドボックス（独立したオリジン）で表示する。`localStorage`・`sessionStorage`・Cookie・
  `history` API・親ページ（`parent` / `top`）への参照・フォーム送信は動作しないため使わない。
  テンプレートのスクリプトはこの制約の範囲で動作する。

## 6. 文章の規約

- 「です・ます」調。SE が読者に直接説明する目線で書く。第三者が外から要約したような表現は使わない。
- 機能名は「ダッシュボードの表記（英語の正式名称）」の形で初出時に併記する（例: 支出上限（Spend limits））。
- 表のセルは 1〜2 文に収める。同じ列の文末表現をそろえる（すべて体言止め、またはすべて「〜します」）。
- 画面に表示されている値（件数・設定値・有効/無効）は正確に転記する。読み取れない値は書かない。
- 画面から読み取れない推測は「〜と考えられます」と明示し、断定しない。推測した箇所は最後の報告で SE に伝える。
- 製品一般論だけで終わらせず、「この環境での読み取り」で設定値と設計意図を結びつける。
- 「AI が生成」「下書き」「レビューが必要」などの制作過程に関するメタな記述を本文に含めない。
- ベータ表示の機能は `<span class="badge b-off">ベータ</span>` を付け、仕様が変わりうることを「本資料の読み方」に書く。

## 7. 仕様の確認

- 機能の仕様・挙動は Cloudflare Docs（developers.cloudflare.com）で確認してから書く。
  Cloudflare Docs の MCP ツールまたは WebFetch を使い、学習済みの知識だけで仕様を断定しない。
- 「本資料の読み方」に「仕様は Cloudflare Docs（YYYY 年 M 月時点）に基づきます」と確認した時点を書く。
- Docs で確認できなかった挙動は、画面の表示から読み取った内容であることを `.note` で明記する。
- 「参考ドキュメント」には実際に確認した URL だけを載せる。URL を推測で作らない。

## 8. 匿名化と共有

- 顧客名は `notes.md` の顧客エイリアスだけを使う。顧客名、ドメイン、メールアドレス、IP アドレス・CIDR、
  アカウント ID・テナント ID・その他の ID、実在の人名を本文に書かない。
- ポリシー名・プロファイル名に顧客固有の名称が含まれる場合は、役割がわかる一般名に置き換える
  （例: `Block-Kyoto-Branch-Social` → `拠点向けソーシャルメディア制限`）。
- テスト・検証・PoC 用と判断できる名称のポリシーやルールは、代表例として取り上げない。
- 画像の機微情報は SE がマスクする（「3. 作業手順」の 4）。本文の `.warn` に共有時の注意を書く必要はない
  （公開前にマスク済みであることが前提）。
- サイトへのアップロード時の公開範囲は既定で「限定」とする。全体公開は SE が判断する。

## 9. 製品別の記載ルール

### 9-1. Cloudflare Zero Trust（Cloudflare One）

- 機能章はダッシュボードの左ナビの順に、取得した画面に合わせて構成する。目安は次のとおり。
  Insights（ログ・分析） / Networks（Tunnel・Routes） / Access（アプリケーション・ポリシー） /
  Gateway（DNS・Network・HTTP・Egress・Resolver） / Device & Access Control（WARP・Device Profile・Posture） /
  Split Tunnel / Integrations（Identity Provider・Posture Provider） / DLP・CASB / Settings。
- **Gateway**: DNS・Network・HTTP から代表的なポリシーを選んで解説する。網羅した一覧とは表現しない。
  - 各ポリシーは、ポリシー名（一般名化）、対象通信（脅威カテゴリなど具体的な条件）、対象ユーザー、端末状態、アクションを書き、
    何を防止・許可するのかを説明する。「特定ドメインへのアクセスを制御する」のような一般論に言い換えない。
  - HTTP は Do Not Inspect を最大 1 件、Do Not Scan を最大 1 件、その他の制御系を最大 4 件。
    Do Not Inspect / Do Not Scan は対象となる主要アプリケーションを具体例として書く。
  - テナント制御の Allow ポリシーは、組織で許可した SaaS テナントだけを利用させる制御として説明する。
- **Egress**: 固定の出口 IP を指定したポリシーだけを解説し、共有出口に戻すデフォルトの除外ポリシーには触れない。出口 IP は書かない。
- **Device & Access Control**: Device Profile は「適用条件 → Profile → 接続・端末制御」の流れを `.flow` で示し、
  Profile ごとの適用対象、接続モード、切断・離脱の制御、自動再接続、Tunnel Protocol、DNS 関連設定を表で説明する。
  - デフォルト Profile は全端末向けではなく、他の Profile の条件に一致しなかった端末・ユーザーへのフォールバックとして説明する。
  - Managed Network、IdP グループなどの分岐は、実際に設定されている条件だけを書く。未設定の分岐を設計例として加えない。
- **Split Tunnel**: Device & Access Control とは別の節にし、各パターンがどの Device Profile に紐づく設定かを明記する。
  - Include（Cloudflare 経由）と Exclude（直接接続）は、実際に 1 件以上設定されている方式だけを書く。
    設定されていない方式は、見出し・説明・「設定なし」の注記も含めて書かない。
  - 宛先はカテゴリ（プライベートネットワーク、会議・コラボレーションサービスなど）で示し、ホスト名・IP は書かない。
- **Identity Provider**: 連携方式、SCIM、グループ連携の設定状況を説明する。SAML の場合は IdP の名称を明記する。
- **Device Posture**: チェックは同じ種別でも統合せず、名称付きで個別に列挙する。種別、対象 OS、有効状態、Gateway ポリシーでの利用状況を書く。
  Posture Provider を使っている場合は、プロバイダー種別と連携の用途を書く。
- **Local Domain Fallback**: 件数は、カスタムで登録し DNS サーバーを指定した設定だけを数える。

### 9-2. その他の製品

- AI Gateway は基準ガイド（`reference/ai-gateway-dashboard-guide.html`）の章立てと記述をそのまま踏襲する。
- その他の製品も 4 章の固定構成に当てはめ、機能章はダッシュボードの左ナビ・タブの順に構成する。

- [ ] 目次と本文の章・節が完全に一致し、本文内リンクの参照先がすべて存在する
- [ ] 各節が「スクリーンショット → 画面の役割 → 項目の詳細 → 仕組み → この環境での読み取り」の順になっている
- [ ] 画面に写っている項目を表で漏れなく説明している
- [ ] すべての画像が `./assets/NN-kebab-case.png` で、alt と「図 N-M」のキャプションがある
- [ ] 機微情報が本文にも画像にも残っていない（画像は SE のマスク確認済み）
- [ ] 仕様の記述を Cloudflare Docs で確認し、確認時点を「本資料の読み方」に書いた
- [ ] 推測を含む記述を「〜と考えられます」と明示し、報告に含めた
- [ ] 入力のない項目（契約概要の行、PoC・オンボーディングの節など）を削除した

## 11. サイトへの登録と更新

1. サイトにログインし、ダッシュボードの「事例 - 設計ガイドをアップロード」（`/portal/cases/new`）を開く。
2. ZIP を選択し、カテゴリ・タグ・公開範囲（既定: 限定）を設定してアップロードする。タイトルは空欄なら `<title>` が使われる。
3. 下書きとして保存され、編集画面に移動する。「プレビュー」で `/cases/<slug>` の表示を確認する。
4. 問題がなければ「公開する」を押す。公開後は `/cases` の一覧、検索、トップページに表示される。
5. 内容を更新するときは、手元の `work/<slug>/` を修正して ZIP を作り直し、編集画面の「ZIP を差し替え」からアップロードする。
   編集画面の本文欄（HTML）での直接修正は軽微な文言修正に限り、同じ修正を手元の `index.html` にも反映して、
   手元のファイルを常に正とする。
